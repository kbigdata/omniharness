## 1. 하네스 엔지니어링이란 무엇인가

### 1.1 정의

**에이전트 하네스(Agent Harness)** 는 언어 모델(LLM)과 외부 세계 사이에 위치하는 인프라 계층이다. 원시 LLM은 텍스트를 예측할 뿐 스스로 행동하지 못한다. 하네스는 그 모델에 다음을 부여한다.

- **도구(Tools)**: 파일 읽기/쓰기, 셸 실행, 웹 접근 등 행동 수단
- **실행 루프(Agentic Loop)**: 도구 호출 → 결과 관찰 → 다음 행동 결정의 다단계 반복
- **컨텍스트/메모리 관리**: 컴팩션(compaction), 진행 상태 파일, 세션 간 인계
- **권한·안전장치(Guardrails)**: 위험 행동 차단, 인간 승인 게이트
- **관측성(Observability)**: 로그, 감사 추적, 텔레메트리

즉, **하네스 엔지니어링은 "모델을 더 똑똑하게 만드는 작업"이 아니라 "모델의 출력이 안전하고 일관되게 실제 결과로 이어지도록 런타임을 설계하는 작업"** 이다. Anthropic 문서의 표현을 빌리면, Claude Code는 언어 모델을 유능한 코딩 에이전트로 만드는 도구·컨텍스트 관리·실행 환경을 제공하는 하네스다.

### 1.2 왜 지금 중요한가

- Anthropic 내부 실험에 따르면, 프런티어 모델(예: Opus 4.5)조차 잘 설계된 하네스 없이 멀티 컨텍스트 윈도우 루프를 돌리면 프로덕션 품질의 앱을 완성하지 못한다. 한 번에 너무 많이 하려 하거나, 일이 끝나지 않았는데 "완료"를 선언하는 실패 패턴이 반복된다.
- "에이전트를 만든다"는 행위는 본질적으로 두 가지 중 하나다 — **(a) 모델을 학습시키거나(RL, fine-tuning), (b) 하네스를 만들거나.** 대다수 실무 개발자가 하는 일은 (b)이며, 이것이 하네스 엔지니어링이 실무 핵심 역량으로 부상한 이유다.
- Claude Code, Codex CLI, Cursor가 서로 다르게 느껴지는 이유는 모델 차이가 아니라 **하네스 설계 선택의 차이**(도구 구성, 권한 모델, 루프 구조)에 있다.

### 1.3 기성 하네스 vs 커스텀 하네스

| 구분 | 기성(Prebuilt) 하네스 | 커스텀 하네스 |
|---|---|---|
| 예시 | Claude Code 기본 도구·권한·루프 | 조직별 오케스트레이션 파이프라인, 규정 준수 게이트 |
| 제공 가치 | 범용 신뢰성 (파일 도구, Bash, 승인 프롬프트) | 조직적 책임성 (감사 로그, 도메인별 차단 규칙) |
| 관계 | 둘은 대체재가 아니라 **레이어로 결합**된다 | 기본 하네스 위에 조직 규칙을 얹는다 |

예: 핀테크 팀이 "결제 로직 PR은 사내 컴플라이언스 린터 필수 통과", "DB 마이그레이션 파일은 인간 승인 없이는 수정 금지", "모든 에이전트 활동은 감사 시스템에 로깅" 같은 요구를 기본 하네스 위에 커스텀 계층으로 구현하는 식이다. 모델도, Claude Code 기본 하네스도 바뀌지 않는다 — 바뀌는 것은 그 사이의 레이어다.

## 2. 패러다임 변천

| 시기 | 핵심 스킬 | 핵심 질문 |
|---|---|---|
| ~2024 | **Prompt Engineering** | 지시문을 어떻게 쓸 것인가 |
| 2024–2025 | **Context Engineering** | 배경 정보(RAG 등)를 어떻게 공급할 것인가 |
| 현재 (병렬 쌍) | **Harness Engineering** | 에이전트 런타임(권한·훅·MCP·도구 표면)을 프로세스 **내부에서** 어떻게 구성할 것인가 |
| 〃 | **Environment Engineering** | 에이전트가 행동하는 세계(OS 사용자·샌드박스·네트워크)를 프로세스 **외부에서** 어떻게 경계지을 것인가 |

핵심 전환: 프롬프트 엔지니어링에서는 엔지니어가 "그 순간 무엇을 할지" 모델에게 말한다. 컨텍스트 엔지니어링에서는 "잘하기 위한 재료"를 조립한다. 로컬 AI 에이전트 시대에는 **하네스를 튜닝하고 작업장을 차려준 뒤, 에이전트가 그 안에서 일하도록 신뢰하는** 방식으로 바뀐다.

온라인 챗봇은 제공자가 하네스·환경을 고정해 두므로 프롬프트와 컨텍스트만이 레버다. 반면 **로컬 에이전트(Claude Code)는 사용자의 파일시스템 안으로 들어오며, 하네스와 환경 모두가 사용자의 설계 대상**이 된다. 아무것도 하지 않으면 에이전트의 능력 상한과 파괴 가능 하한은 모두 "내 OS 사용자가 할 수 있는 모든 것"과 같아진다.

> **실무 관찰**: 같은 Claude Code, 같은 하드웨어, 같은 코드베이스에서도 엔지니어 간 생산성 격차가 극심한데, 그 차이는 거의 전적으로 하네스/환경 작업량에서 온다. (§11의 3가지 패턴 참조)

## 3. 에이전트 하네스의 핵심 구성요소

현대적 프로덕션 하네스는 다음의 레이어드 시스템이다.

1. **도구 오케스트레이션(Tool Orchestration)** — 모델을 수동적 텍스트 생성기에서 다단계 자율 실행자로 바꾸는 중추. 엄격한 입력 스키마를 가진 도구들이 모델의 의도를 안전하고 구조화된 작업으로 변환한다.
2. **실행 루프와 상태 관리** — 멀티턴 대화 상태, 도구 결과 피드백, 컨텍스트 컴팩션.
3. **검증(Verification)** — 단위 테스트, E2E 테스트, 브라우저 자동화, 별도 평가자 에이전트.
4. **메모리/인계 아티팩트** — 진행 로그, git 히스토리, 기능 목록 파일 등 세션 간 상태 전달 수단.
5. **가드레일(Guardrails)** — 권한 규칙, 훅, 샌드박스, 인간 승인 게이트.
6. **관측성(Observability)** — JSONL 도구 호출 로그, OpenTelemetry, 감사 추적.

Claude Code는 이 중 1, 2, 5를 기본 제공하고(약 19개의 권한 게이트 도구 — 파일 읽기/편집, Bash, Git, WebFetch, 노트북 편집, MCP 호출; LSP·서브에이전트 생성·내부 조정 도구까지 포함하면 40개 수준이라는 분석도 있음), 3, 4, 6은 사용자가 설정과 스크립트로 조립하는 영역이다. **이 조립이 곧 Claude Code 하네스 엔지니어링이다.**

## 4. Anthropic의 장기 실행 하네스 연구

### 4.1 "Effective Harnesses for Long-Running Agents" (2025-11-26)

**문제 정의**: 장기 실행 에이전트는 불연속적 세션으로 일하며, 새 세션은 이전 기억이 없는 상태로 시작한다. "인수인계 없이 교대 근무하는 엔지니어 팀"에 비유된다. 컴팩션만으로는 부족하다.

**관찰된 2대 실패 모드**

| 실패 모드 | 증상 |
|---|---|
| 원샷 시도(One-shotting) | 한 세션에서 앱 전체를 만들려다 컨텍스트 고갈 → 절반 구현된 미문서화 기능을 다음 세션이 떠안음 |
| 조기 완료 선언(Premature victory) | 후속 세션이 기존 진행을 보고 "다 됐네" 하고 종료 |

**해법: 2단 하네스 구조** (Claude Agent SDK 기반, 코드 예제는 `anthropics/claude-quickstarts/autonomous-coding`)

1. **Initializer Agent (최초 세션 전용 프롬프트)** — 환경 기반 구축
   - `init.sh`: 개발 서버 기동/실행 방법을 스크립트화
   - `claude-progress.txt`: 세션 간 작업 로그
   - 최초 git 커밋: 베이스라인 확정
   - **기능 목록 파일(JSON)**: 사용자의 고수준 프롬프트를 200개 이상의 E2E 기능 명세로 확장, 전부 `"passes": false`로 초기화
2. **Coding Agent (이후 모든 세션)** — 점진적 진행 + 인계 아티팩트 갱신
   - 세션 시작 시: `pwd` → progress 파일·git log 읽기 → 기능 목록에서 미완료 최우선 기능 1개 선택
   - **한 번에 한 기능만** 작업 (원샷 방지의 핵심)
   - 세션 종료 시: 서술적 커밋 메시지로 git 커밋 + progress 파일 갱신 → "main에 머지 가능한 깨끗한 상태"로 마감

**핵심 디테일**

- 기능 목록은 **Markdown이 아닌 JSON**으로: 모델이 JSON 파일을 임의로 고치거나 덮어쓸 확률이 낮다.
- 기능 항목 수정은 `passes` 필드 토글만 허용하고, "테스트를 삭제·수정하는 것은 용납되지 않는다" 수준의 강한 문구로 못 박는다.
- **E2E 자가 검증 강제**: 명시적으로 시키지 않으면 모델은 유닛 테스트나 `curl`로만 확인하고 끝낸다. Puppeteer MCP 같은 브라우저 자동화를 주고 "인간 사용자처럼 테스트하라"고 지시하면 코드만으로는 안 보이는 버그를 잡는다. (단, 브라우저 네이티브 alert 모달은 못 본다는 등 시각/도구 한계는 남음)

**실패 모드 ↔ 해법 매핑 (원문 요약표)**

| 문제 | Initializer 행동 | Coding Agent 행동 |
|---|---|---|
| 프로젝트 전체 조기 완료 선언 | 기능 목록 JSON 생성 | 세션 시작 시 목록 읽고 기능 1개 선택 |
| 버그/미문서 상태로 환경 방치 | 초기 git repo + progress 파일 작성 | 시작 시 progress·git log 확인 + 기본 동작 테스트, 종료 시 커밋 + progress 갱신 |
| 기능을 조기 "완료" 처리 | 기능 목록 JSON 생성 | 신중한 테스트 후에만 `passes: true` |
| 앱 실행법 파악에 시간 낭비 | `init.sh` 작성 | 시작 시 `init.sh` 읽고 실행 |

### 4.2 "Harness Design for Long-Running Application Development" (2026-03-24)

후속 연구로, **계획(Planning) / 생성(Generation) / 평가(Evaluation)를 분리한 멀티에이전트 하네스**를 제시했다.

- **Generator–Evaluator 분리 (GAN 유사 구조)**: LLM이 자기 출력을 스스로 평가하면 품질이 평범해도 과대평가하는 경향이 있다. 만드는 에이전트와 판정하는 에이전트를 구조적으로 분리하면 평가자는 생성 과정을 못 봤으므로 매몰비용 편향이 없다. Anthropic 엔지니어링 리드는 "작업하는 에이전트와 판정하는 에이전트의 분리가 강력한 레버"라고 요약했다.
- **프런트엔드 디자인 평가 기준 4종**: 디자인 품질(design quality), 독창성(originality), 완성도(craft), 기능성(functionality). 평가자는 Playwright MCP로 라이브 페이지를 직접 조작하며 상세 비평을 생성자에게 피드백한다. 사이클은 5~15회, 최대 4시간까지 반복되며, 안전하고 평범한 레이아웃에서 벗어나 더 과감한 결과를 끌어냈다.
- **가중치 = 손실 함수**: 모델이 기본적으로 craft/functionality는 잘하므로 design/originality에 더 높은 가중치를 줘 미적 리스크 테이킹을 유도했다. (RL 관점: 평가 루브릭이 곧 loss function, 평가자가 critic, 생성자가 그 loss를 반복적으로 최소화)
- **평가자 캘리브레이션 필요**: 초기 평가자는 문제를 발견하고도 "큰 문제는 아니다"라고 스스로 무마하는 관대함을 보였다. few-shot 예시와 점수 기준으로 여러 차례 보정해야 유용한 QA 판정이 나왔다.
- **컴팩션 대신 컨텍스트 리셋 + 구조화 인계**: 컴팩션은 컨텍스트를 보존하지만 모델이 한계에 접근하며 소극적으로 변할 수 있다. 대신 컨텍스트를 리셋하고 구조화된 인계 아티팩트로 다음 에이전트가 정의된 상태에서 이어가게 했다.

### 4.3 하네스는 "썩는다" — 모델 발전과 하네스의 수명

Anthropic의 후속 글(Managed Agents)에서 강조된 중요한 교훈:

> 하네스는 "모델이 혼자서는 못하는 것"에 대한 가정을 인코딩한다. 모델이 발전하면 그 가정은 낡는다.

대표 사례: Sonnet 4.5는 컨텍스트 한계가 다가오면 작업을 서둘러 마무리하는 **"context anxiety(컨텍스트 불안)"** 행동을 보였고, 이를 하네스의 컨텍스트 리셋으로 해결했다. 그러나 Opus 4.5에서는 그 행동 자체가 사라져, 리셋 장치가 **죽은 무게(dead weight)** 가 되었다.

→ **시사점**: 하네스 구성요소마다 "이건 어떤 모델 결함을 보완하는가?"를 주석으로 남기고, 모델 업그레이드 시마다 해당 가정을 재검증하라. 최대 오케스트레이션이 항상 정답이 아니며, 유용한 스캐폴드는 모델이 발전함에 따라 달라진다.

## 5. Claude Code의 3계층 모델

Claude Code 하네스 엔지니어링에서 가장 비싼 실수는 **"권고(advise)"와 "강제(enforce)"를 혼동**하는 것이다. 규칙이 사는 곳은 세 곳이다.

| 계층 | 수단 | 역할 | 할 수 없는 것 |
|---|---|---|---|
| **Intent (권고)** | `CLAUDE.md`, 프롬프트 | 에이전트가 **의도**하는 바를 형성 | 차단·거부·감사 불가 |
| **Harness (프로세스 내 강제)** | `settings.json`의 `permissions`, `hooks`, MCP 게이트 | 에이전트가 **디스패치할 수 있는 도구 호출**을 제한 | 일단 스폰된 서브프로세스의 후속 행동은 못 잡음 |
| **Environment (프로세스 외 강제)** | OS 사용자/ACL, 컨테이너, 샌드박스, 네트워크 필터 | 에이전트가 시스템에서 **실제로 실행 가능한 것**을 제한 | "이 repo는 프로덕션" 같은 도메인 의도 표현은 상위 계층의 일 |

### 5.1 흔한 오해부터 제거

`CLAUDE.md`에 "하지 마시오" 목록을 넣으면 에이전트가 지킬 것이라는 믿음은 위험하다. `CLAUDE.md`는 **컨텍스트에 들어가는 텍스트일 뿐 강제 계층이 없다.** 충분히 확신에 찬 환각, 모호한 지시, 컨텍스트 절단 한 번이면 무력화될 수 있다.

> **경험칙**: `CLAUDE.md`에 쓰는 모든 문장은 "에이전트가 그 줄의 존재를 잊어도 지킬 만한" 문장이어야 한다. 그보다 엄격한 규칙은 하네스로, 오작동하는 서브프로세스에서도 살아남아야 하는 규칙은 환경으로 내려라.

### 5.2 같은 규칙을 5개 층에서 표현하기

규칙: **"`secrets/` 안의 파일을 절대 삭제하지 마라"**

1. **(Intent)** `CLAUDE.md`: "`secrets/`는 읽기 전용으로 취급 — 삭제·수정 금지." → 대체로 지켜진다. 대체로.
2. **(Harness)** `permissions.deny`: `"Bash(rm secrets/*)"`, `"Bash(rm -rf secrets*)"`, `"Write(secrets/**)"` → 도구 디스패처가 스폰 전에 거부.
3. **(Harness)** `PreToolUse` 훅: 제안된 명령을 검사해 `secrets/`를 건드리면 비정상 종료. 위 리터럴 패턴과 다른 형태의 명령까지 포착.
4. **(Environment)** OS 권한: `chmod 000 secrets` + 다른 사용자 소유 → 프로세스 내 검사를 우회해도 커널이 거부.
5. **(Environment)** 샌드박스: `secrets/`가 아예 마운트되지 않은 컨테이너 → 삭제할 대상 자체가 에이전트의 세계에 없음.

**프로덕션에서는 최소 3개 층(하네스 1+ 환경 1+ 포함)을 겹쳐라. 2개는 취약하고, 1개는 연극이다.**

## 6. Claude Code 적용 ① — settings.json 권한 모델

### 6.1 설정 파일 우선순위 (높은 것이 이김, 배열은 병합)

1. **Managed settings** — IT 관리(MDM/관리 콘솔/OS 정책 파일). 하위에서 재정의 불가
2. **CLI 인자** — `--permission-mode`, `--allowedTools` 등 (해당 호출만)
3. **`.claude/settings.local.json`** — 프로젝트 내 개인용(미커밋)
4. **`.claude/settings.json`** — 프로젝트 공유(커밋, 팀의 "공개 인터페이스")
5. **`~/.claude/settings.json`** — 개인 전역 기본값

배열은 병합되며 **deny가 스코프와 무관하게 먼저 평가**되므로, `~/.claude/settings.json`에 엄격한 전역 deny 목록을 두면 모든 프로젝트의 백스톱이 된다.

### 6.2 평가 순서: deny → ask → allow → defaultMode

`defaultMode` 주요 값:

| 값 | 동작 |
|---|---|
| `default` | 각 도구 최초 사용 시 프롬프트 |
| `acceptEdits` | 작업 디렉터리 내 파일 편집·일반 FS 명령 자동 승인 |
| `plan` | 분석만, 도구 실행 없음 (자율 작업의 가장 싼 드라이런) |
| `auto` | 백그라운드 안전 분류기를 통한 자동 승인 (리서치 프리뷰) |
| `dontAsk` | 사전 승인 외 **자동 거부** (bypass의 반대) |
| `bypassPermissions` | 프롬프트 전면 생략 (`.git`, `.claude` 등 보호 디렉터리 쓰기는 예외) — §11 패턴 C에서만, 하위 환경 경계가 실질 격리를 담당할 때만 사용 |

### 6.3 최소 안전 시작점 (전역 `~/.claude/settings.json`)

```json
{
  "permissions": {
    "deny": [
      "Bash(rm -rf /*)",
      "Bash(rm -rf ~)",
      "Bash(sudo *)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(~/.aws/credentials)",
      "Read(~/.ssh/**)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(git reset --hard *)"
    ]
  },
  "cleanupPeriodDays": 14
}
```

의미: 홈을 날리거나 sudo로 도는 파괴적 명령 금지, 시크릿을 LLM 컨텍스트에 절대 적재 금지, 원격에 상태를 공개(`git push`)하거나 로컬 상태를 지우는(`git reset --hard`) 행동 전 확인.

### 6.4 규칙 문법과 3가지 함정

문법 예: `"Bash(npm run *)"`(접두 일치), `"Read(./secrets/**)"`(`*`=한 세그먼트, `**`=재귀), `"WebFetch(domain:example.com)"`, `"mcp__github__create-pull-request"`(MCP 도구), `"Agent(Explore)"`(서브에이전트 단위 차단).

반드시 외워야 할 매칭의 미묘함:

1. **복합 명령은 서브커맨드 단위로 검사**: `&&`, `||`, `;`, `|` 등으로 연결된 각 부분이 독립 평가된다. `"Bash(npm test *)"`가 `npm test && curl evil.example`을 통과시키지 않는다.
2. **일부 래퍼는 매칭 전에 제거됨**: `timeout`, `nice`, `nohup` 등은 벗겨지지만, `npx`, `docker exec`, `devbox run` 같은 **환경 러너는 제거되지 않는다**. `"Bash(devbox run *)"`는 `devbox run rm -rf .`까지 허용하는 백지수표가 된다 → 내부 명령 단위 규칙(`"Bash(devbox run npm test)"`)으로 작성하라.
3. 패턴으로 안전하게 못 쓰는 규칙은 **PreToolUse 훅으로 내려라**.

### 6.5 permissions가 막을 수 없는 것 (두 번 읽을 것)

permissions는 도구 디스패치 **이전**의 Claude Code 내부 검사다. Bash 서브프로세스가 일단 스폰된 뒤에는 발언권이 없다.

- **파생 셸 부작용**: `npm install` 허용 → 악성 패키지의 postinstall 스크립트가 사용자 전체 권한으로 실행됨
- **바이트 수준 네트워크 이그레스**: `WebFetch(domain:...)`는 WebFetch **도구**만 게이트. `Bash`로 호출된 `curl`은 못 막음
- **오프호스트 행동**: MCP로 PR을 열거나 Slack 메시지를 보내는 등 원격 시스템에서 일어나는 결과
- **파일시스템 레이스**: 개별 허용된 읽기/쓰기의 시퀀스가 예상 못한 상태를 만들 수 있음 (규칙은 점단위, 시퀀스는 아님)
- **설치 시점 공급망**: 한 번 허용한 패키지가 미래 설치에서 다른 post-install을 실을 수 있음

→ 각 공백의 답은 한 층 아래: 훅(셸 부작용), OS 사용자 경계(자식 프로세스), 샌드박스(네트워크·FS), 락파일 정책 + `npm ci`(공급망).

## 7. Claude Code 적용 ② — Hooks

`permissions`가 선언적(패턴 목록)이라면 **훅은 프로그램적**이다. 라이프사이클 이벤트(`PreToolUse`, `PostToolUse`, `SessionStart`, `Stop` 등)에서 셸 스크립트·HTTP 엔드포인트·다른 에이전트를 실행하며, 제안된 액션이 JSON으로 stdin에 들어온다. **"뻔한 패턴 차단"을 "의미적으로 위험한 모든 것 차단"으로 끌어올리는 실질적 강제 계층**이다.

### 7.1 대표 활용 패턴

| 훅 | 용도 예 |
|---|---|
| `PreToolUse` | 파괴적 명령 의미 검사 후 차단(비정상 종료=차단), 입력 변형, 사내 컴플라이언스 린터 게이트 |
| `PostToolUse` | 편집 직후 포매터/린터/타입체커 자동 실행, 실패 시 피드백을 모델에 주입 |
| `SessionStart` | progress 파일·git log 자동 로드(장기 실행 인계) |
| `Stop` | 종료 전 "기능 목록 갱신했는가, 커밋했는가" 게이트 — 미완이면 종료 거부 |

관련 보안 키: `disableAllHooks`(킬 스위치), `allowedHttpHookUrls`(HTTP 훅 목적지 화이트리스트 — 설정 실수로 임의 URL 유출 방지), `httpHookAllowedEnvVars`.

### 7.2 공식 예제 저장소

`anthropics/cwc-long-running-agents` 저장소는 2025-11/2026-03 두 하네스 논문의 패턴을 **독립적인 짧은 훅 스크립트 + 평가자 서브에이전트**로 제공한다. 각 프리미티브는 의존성 없는 단일 파일이며, `.claude/` 디렉터리를 프로젝트에 복사하고 훅 스크립트에 실행 권한을 주는 것으로 시작한다. "읽고 골라 쓰는(read and cherry-pick)" 재료 모음이지 턴키 하네스가 아니라는 점에 유의.

## 8. Claude Code 적용 ③ — CLAUDE.md, 서브에이전트, Skills, MCP

### 8.1 CLAUDE.md — 가볍지만 지속적인 하네스 커스터마이징

리포지토리의 `CLAUDE.md`는 모든 세션에 팀 규약을 자동 주입한다. 역할은 **Intent 계층**: 코딩 컨벤션, 빌드/테스트 명령, 아키텍처 개요, 디렉터리 의미("`secrets/`는 읽기 전용") 등. 강제력이 없으므로 §5의 원칙대로 작성하고, 강제가 필요한 항목은 permissions/훅에 중복 기재한다.

권장 구조 예:

```markdown
# 프로젝트 개요
- 목적, 기술 스택, 핵심 디렉터리 의미

# 빌드/테스트
- ./init.sh 로 개발 서버 기동
- npm test (유닛), npm run e2e (E2E)

# 컨벤션
- 커밋 메시지 형식, 브랜치 전략

# 경계 (권고 — 강제는 settings.json/hooks가 담당)
- secrets/, migrations/ 는 수정 금지
- 외부 API 키는 절대 코드에 하드코딩 금지
```

### 8.2 서브에이전트(Subagents)

`.claude/agents/`에 정의하는 별도 컨텍스트의 전문 에이전트. 하네스 관점의 핵심 용도는 **평가자(Evaluator) 분리**(§10)와 탐색/계획 작업의 컨텍스트 격리다. `"Agent(이름)"` 권한 규칙으로 특정 서브에이전트 사용 자체를 차단할 수도 있다.

### 8.3 Skills

`.claude/skills/*/SKILL.md`로 도메인 절차 지식을 패키징한다. 하네스 관점에서는 "도구 표면의 문서화된 확장"으로, 에이전트가 특정 작업 유형에서 따라야 할 검증 절차·금지 사항을 작업 시점에 컨텍스트로 끌어온다. (실제 사례: Harness.io 같은 벤더는 CI/CD 운영 전체를 CLAUDE.md + skills + MCP 서버 조합의 워크플로 시스템으로 배포한다.)

### 8.4 MCP 서버 — 외부 도구 표면의 게이트

`.mcp.json`으로 서버를 정의하고, `settings.json`의 `enabledMcpjsonServers` / `disabledMcpjsonServers` / `allowedMcpServers` / `deniedMcpServers`로 **어떤 서버가 실제 로드되는지** 게이트한다. 개별 MCP 도구는 `"mcp__서버__도구"` 권한 규칙으로 통제한다.

주의: MCP 게이트는 "어떤 호출이 승인되는가"까지만 책임진다. **승인된 호출 뒤에서 토큰이 무엇을 할 수 있는지는 게이트 밖**이므로, MCP용 자격증명은 최소 권한·단기 토큰으로 발급하라(`apiKeyHelper`로 동적 주입 가능).

### 8.5 Sandbox 설정 — 환경 계층의 진입점

`settings.json`의 `sandbox` 키는 Bash 도구와 그 자손에 OS 수준 샌드박스를 적용한다(macOS: Seatbelt, Linux/WSL2: bubblewrap + socat 필요).

- `sandbox.enabled`: 활성화
- `sandbox.filesystem.allowRead/denyRead/allowWrite/denyWrite`: FS 경계
- `sandbox.network.allowedDomains/deniedDomains`: 이그레스 도메인 화이트리스트 — **permissions가 못 막는 `curl`을 여기서 막는다**
- `sandbox.autoAllowBashIfSandboxed`(기본 true): 샌드박스가 게이트하므로 Bash별 프롬프트 생략

더 강한 격리는 Docker/devcontainer/VM + 비특권 OS 사용자 + 자격증명 비탑재로 구성한다(§11 패턴 C).

## 9. Claude Code 적용 ④ — 장기 실행 하네스 패턴 구현

§4.1의 Agent SDK 연구를 Claude Code 프로젝트에 이식하는 실전 레시피.

### 9.1 인계 아티팩트 4종 세트

```
project/
├── init.sh                 # 개발 서버 기동 + 스모크 테스트 절차
├── claude-progress.txt     # 세션 간 작업 로그 (append-only 운영)
├── feature_list.json       # E2E 기능 명세 (passes: true/false)
└── .claude/
    ├── settings.json       # 권한 + 훅
    ├── hooks/              # 세션 시작/종료 게이트 스크립트
    └── agents/evaluator.md # 평가자 서브에이전트
```

`feature_list.json` 항목 형식 (Anthropic 원문 구조):

```json
{
  "category": "functional",
  "description": "New chat button creates a fresh conversation",
  "steps": [
    "Navigate to main interface",
    "Click the 'New Chat' button",
    "Verify a new conversation is created"
  ],
  "passes": false
}
```

### 9.2 세션 프로토콜 (CLAUDE.md 또는 커스텀 명령으로 고정)

**세션 시작 의례**
1. `pwd`로 작업 디렉터리 확인
2. `claude-progress.txt` + `git log --oneline -20` 으로 직전 상태 파악
3. `init.sh` 실행 → 기본 E2E 스모크 테스트로 "깨진 상태" 여부 즉시 확인 (깨졌으면 새 기능 전에 수리)
4. `feature_list.json`에서 미완료 최우선 기능 **1개** 선택

**세션 종료 의례**
1. 작업 기능 E2E 검증 (브라우저 자동화 등 인간 사용자 관점) 후에만 `passes: true`
2. 서술적 메시지로 git 커밋
3. `claude-progress.txt`에 요약 추가

이 의례를 **권고(CLAUDE.md)에만 두지 말고 `SessionStart`/`Stop` 훅으로 강제**하면 신뢰도가 크게 올라간다.

### 9.3 검증 도구 제공

웹 앱이면 Puppeteer/Playwright MCP를 연결해 "모든 테스트를 인간 사용자가 하듯 수행"하도록 지시한다. 검증 도구 제공은 성능을 극적으로 개선하지만, 시각·도구의 한계(예: 네이티브 alert 모달 미인식)로 못 잡는 버그 유형이 남는다는 점은 설계에 반영하라.

## 10. Claude Code 적용 ⑤ — Generator–Evaluator 루프와 /goal

### 10.1 내장 기능: /goal

Claude Code의 `/goal` 명령은 **생성자/평가자 루프를 기본 제공**한다: 완료 조건을 설정하면 별도의 빠른 모델이 매 턴 후 조건 충족을 검사하고, 충족될 때까지 반복한다.

### 10.2 커스텀 평가자 서브에이전트

`/goal`보다 정교한 통제가 필요하면 §4.2 구조를 직접 조립한다.

1. `.claude/agents/evaluator.md`에 평가자 정의 — **생성 과정을 보지 않은 신선한 컨텍스트**에서 산출물만 평가
2. 평가 루브릭을 명시적 점수 기준 + few-shot 예시로 캘리브레이션 (초기 평가자의 "관대함" 편향 보정 필수)
3. 도메인에 맞는 기준 가중치 설정 — 모델이 이미 잘하는 축은 낮게, 끌어올리고 싶은 축은 높게
4. 평가자에게 실측 도구 제공 (웹이면 Playwright MCP로 라이브 조작, 백엔드면 실제 API 호출 스크립트)
5. 생성→평가→비평 반영 사이클을 5~15회 수준으로 반복

> RL 개발자 관점의 매핑: **루브릭 = loss function, 평가자 = critic, 생성자 = actor.** Actor-Critic 구조를 가중치 업데이트 없이 컨텍스트/프롬프트 수준에서 재현하는 것과 같다.

## 11. 3가지 레퍼런스 운영 패턴

| | 패턴 A: Approval-First | 패턴 B: Curated Allow-list | 패턴 C: Sandboxed Full-Auto |
|---|---|---|---|
| 하네스 작업 | 없음 | 상당 | 상당 |
| 환경 작업 | 없음 | 없음 | 상당 |
| 구성 | 기본값, 거의 매 단계 승인 | 선별된 allow + 파괴 행동 deny + PreToolUse 백스톱 + 정돈된 CLAUDE.md | Docker 컨테이너, 비특권 사용자, 자격증명 미탑재, 도메인 화이트리스트, JSONL 전체 로깅, `bypassPermissions` |
| 적합 용도 | 처음 며칠, 민감 코드베이스 읽기 위주 | 일상 개발 (대부분의 편집·테스트가 무프롬프트 진행) | 야간 무인 자율 작업: 리팩토링, 마이그레이션, 배치 수정 |
| 리스크 | 매우 낮음 (인간 상시 개입) | 낮음 (deny+훅이 최악 케이스 포착) | 격리 경계가 담보 (아침에 감사 로그 검토) |

핵심: 셋 다 같은 Claude Code, 같은 모델이다. **차이는 하네스/환경 스택을 얼마나 내려갔느냐뿐이며, 그것이 곧 생산성 상한과 사고 하한을 동시에 결정한다.**

`bypassPermissions`는 패턴 C에서만, 그것도 **하위 환경 경계(OS 사용자·컨테이너·네트워크 필터)가 실질 격리를 수행하고 있을 때만** 정당화된다.

## 12. 안티패턴과 주의점

1. **CLAUDE.md를 보안 경계로 착각** — 권고는 강제가 아니다. (§5.1)
2. **단일 계층 방어** — "deny 규칙 넣었으니 끝"은 연극이다. 하네스 1+ 환경 1+ 포함 3겹이 기본.
3. **환경 러너에 와일드카드 allow** — `"Bash(npx *)"`, `"Bash(docker exec *)"`는 백지수표. (§6.4)
4. **시크릿을 컨텍스트에 적재** — `.env`, `~/.ssh`, 클라우드 자격증명은 deny-read가 기본값이어야 한다.
5. **자기 평가 신뢰** — 생성자가 자기 출력을 판정하게 두면 과대평가한다. 평가자 분리. (§10)
6. **Markdown으로 상태 파일 관리** — 기능 목록 등 모델이 멋대로 고치면 안 되는 상태는 JSON + 강한 수정 금지 문구. (§4.1)
7. **하네스 화석화** — 모델 업그레이드 후에도 낡은 보정 장치(예: context anxiety용 리셋)를 방치. 구성요소별로 "보완 대상 가정"을 문서화하고 주기 재검증. (§4.3)
8. **검증 단계 생략** — E2E 검증 도구와 명시적 지시 없이는 모델이 "유닛 테스트 통과 = 기능 완료"로 비약한다. (§4.1, §9.3)
9. **과잉 오케스트레이션** — 절차적 if-else 파이프라인에 LLM을 노드로 끼워 넣는 것은 에이전트가 아니다. 지능은 모델이 공급하고, 하네스는 행동 공간과 안전 경계를 공급한다는 분업을 지켜라.

## 14. 트레이딩 시스템 개발 워크플로에의 시사점

강화학습/신경망 기반 트레이딩 시스템 개발에 이 프레임을 적용할 때의 매핑:

1. **feature_list.json → 검증 가능한 시스템 요구 명세**: "백테스트 엔진이 look-ahead bias 없이 OHLCV를 소비한다", "주문 시뮬레이터가 부분 체결을 처리한다" 같은 E2E 검증 단계가 붙은 기능 명세로 장기 작업을 분해.
2. **Generator–Evaluator → 전략 코드와 검증의 구조적 분리**: 전략/모델 코드를 작성하는 에이전트와, 신선한 컨텍스트에서 데이터 누수·과적합 징후·체결 가정의 비현실성을 점검하는 평가자 에이전트를 분리. 루브릭(예: 재현성, 누수 부재, 리스크 한도 준수)이 곧 loss function이라는 관점은 RL 실무와 직결된다.
3. **환경 계층이 특히 중요**: 실거래 API 키·브로커 자격증명은 **에이전트 세계에 아예 존재하지 않게**(미탑재 컨테이너) 하는 것이 원칙. 라이브 트레이딩 엔드포인트는 `sandbox.network` 도메인 화이트리스트에서 제외하고, 백테스트/페이퍼 환경만 노출.
4. **`migrations/`·리스크 한도 설정 파일 = 결제 로직과 동급**: deny + 훅 + 인간 승인(ask)의 3겹으로.
5. **하네스 가정 문서화**: 모델 세대 교체가 빠른 만큼, "이 훅은 모델의 어떤 약점을 보완하는가"를 기록해 두는 습관이 유지보수 비용을 크게 줄인다.

# Part 2 — omni-harness 갭분석 (Part 1 기준)

> 대상: 이 저장소(`omni-harness/`). Claude Code를 `claude-agent-sdk`로 헤드리스 구동하는 얇은 Python 드라이버 + 카파시 위키 + Hermes 자동 스킬 생성.
> 결론 한 줄: **자기개선 "지붕"(Hermes·위키)은 얹었지만, 보고서가 하네스의 본체로 규정한 강제 계층(permissions/hooks)·환경 계층·신선-컨텍스트 검증·세션 간 인계가 비어 있다.**

## 2-1. 3계층 모델(§5)로 본 현재 상태 — 가장 중요한 진단

| 계층 | 보고서 요구 | omni-harness 현재 | 판정 |
|---|---|---|---|
| **Intent (권고)** | CLAUDE.md/AGENTS.md | `template/AGENTS.md`(카파시 헌법) | ✅ 있음 |
| **Harness (프로세스 내 강제)** | settings.json `permissions`(deny/ask)·**hooks**·MCP 게이트·`can_use_tool` | `template/.claude/settings.json` = `{"$schema":...}` **거의 빈 파일**, hooks **0개**, `can_use_tool` **미사용**, `permissions.py`/`observability.py` **파일조차 없음** | ❌ **사실상 없음** |
| **Environment (프로세스 외 강제)** | sandbox/컨테이너/네트워크 필터/비특권 사용자 | **전무** | ❌ **전무** |

→ 보고서 기준 **"2겹은 취약, 1겹은 연극"**(§5.2). omni-harness는 안전 측면에서 **Intent 1겹 = 연극**.

## 2-2. 실제로 저지른 안티패턴 (§12에서 명시 경고)

| 보고서 경고 | omni-harness가 한 일 | 증거 |
|---|---|---|
| **§12.5 자기평가 금지** — 평가자는 생성을 못 본 신선 컨텍스트 | `AgentVerifier`가 **같은 세션을 resume**해 자기 채점 | `verify.py` `AgentVerifier.verify`: `self._options.model_copy(update={"resume": result.session_id})`; 그걸 테스트로 못박음(`test_agent_verifier_pass_and_fail`) |
| **§6.2/§11 `bypassPermissions`는 환경 격리가 실질 격리할 때만** | 실 검증을 **호스트 temp 디렉터리 + `bypassPermissions`**(환경 격리 0)로 수행 | 실구동 검증 스크립트의 `permission_mode="bypassPermissions"` |

## 2-3. 핵심 구성요소(§3) 대조표

| §3 구성요소 | omni-harness | 판정 |
|---|---|---|
| ① 도구 오케스트레이션 | Claude Code 네이티브 위임(SDK) | ✅ |
| ② 실행 루프/상태 | `loop.run_until_verified`(단일 세션 retry) | ⚠️ 세션 간 인계 없음 |
| ③ 검증 | `CommandVerifier`(결정론) ✅ / `AgentVerifier`(자기평가) ❌ / 신선-컨텍스트 평가자·루브릭·캘리브레이션 없음 | ❌ |
| ④ 메모리/인계 | 카파시 위키(지식) ✅ / **작업상태 인계(progress.txt·feature_list.json·init.sh) 없음** | ⚠️ |
| ⑤ 가드레일 | permissions·hooks·샌드박스 전무 | ❌ |
| ⑥ 관측성 | `RunResult`에 비용·도구호출만 / JSONL·감사추적 없음 | ❌ |

## 2-4. 장기 실행(§4·§9) 관점의 구조적 결함

보고서의 장기실행 하네스는 **"기억 없는 교대근무"**를 전제로 *컨텍스트 리셋 + 구조화 인계*로 푼다. omni-harness의 "지속 루프"는 **단일 프로세스에서 `resume`로 같은 세션을 이어가는 retry**다 → 진짜 긴 작업에선 보고서가 말한 one-shotting/context exhaustion 실패 모드를 **그대로** 겪는다. 빠진 것:
- 작업 분해(one-feature-per-session), `claude-progress.txt`, `feature_list.json`(JSON), `init.sh`
- `SessionStart`/`Stop` 의례 강제(현재 hooks 0)
- 컨텍스트 리셋 + 구조화 인계(현재는 단일세션 resume)
- 참고: omni-harness의 "위키"는 *feedforward 지식*이지 *작업상태 인계*가 아니다 — 보고서는 둘을 구분하는데 omni-harness는 후자를 누락.

## 2-5. omni-harness가 잘했거나 보고서 범위를 넘어선 것 (공정한 평가)

- ✅ **얇은 설계** — Claude Code 네이티브 재구현 안 함 → §12.9(과잉 오케스트레이션) 회피
- ✅ **결정론 컨트롤러 + 추론 센서 분리** — `CommandVerifier` + 결정론 게이트 `gate.py`
- ✅ **Hermes 자동 스킬 생성 + 카파시 위키** — 보고서가 깊게 다루지 않은 *자기개선/스킬 induction* 레이어(진짜 추가가치)
- ✅ **Mock 백엔드 테스트 seam** — transport/제어 로직 분리(좋은 하네스 실천), 오프라인 41테스트

→ 즉 omni-harness는 **"제대로 된 하네스/환경이 깔려 있다고 가정한 위에 얹는 자기개선 레이어"**로서는 합리적. 문제는 그 *가정된 기초*를 안 깔았다는 것.

## 2-6. 방향성 — 무엇을, 어떤 순서로 (보고서 Phase에 매핑)

**선결: 정체성 재정의** — (a) *완전한 하네스*로 키울지, (b) 정직하게 *"Hermes+위키 자기개선 레이어"*로 좁히고 기초는 표준 Claude Code 설정에 맡길지. (a)라면 P0가 필수 선행.

**P0 — 안전 기초 (보고서의 본론, 현재 0겹)**
1. **Harness 강제 계층**: `template/.claude/settings.json`에 §6.3 deny/ask 베이스라인 + `ClaudeCodeBackend`에 `can_use_tool` 정책 배선(미존재 `permissions.py` 구현). **기본 permission_mode를 bypass가 아닌 안전 모드로.**
2. **Hooks**(PreToolUse/PostToolUse/Stop): 의미 기반 파괴 차단 + 편집후 린트 + "검증·커밋 전 Stop 거부". (현재 0)
3. **검증 자기평가 결함 수정**: `AgentVerifier`를 resume 금지 → **신선 컨텍스트 평가자(별 세션/서브에이전트)**로. 코드 작업 기본은 `CommandVerifier`.

**P1 — 장기 실행 정합성**
4. **인계 아티팩트**(progress.txt·feature_list.json(JSON)·init.sh) + SessionStart/Stop 훅 + one-feature-per-session + 컨텍스트 리셋.
5. **관측성**: PostToolUse 훅으로 도구호출 JSONL 감사 로그.

**P2 — 규율**
6. **하네스 화석화 방지(§4.3)**: 각 구성요소에 "이건 모델의 어떤 약점을 보완하나" 주석 + 모델 업그레이드 시 재검증.
7. (선택) Generator–Evaluator 루브릭/가중치/캘리브레이션(§10).

## 2-7. 한 줄 결론

> omni-harness는 **카파시 위키 + Hermes 자기개선이라는 "지붕"은 잘 얹었지만**, 보고서가 하네스의 *본체*로 규정한 **강제 계층(permissions/hooks)·환경 계층·신선-컨텍스트 검증·세션 간 인계**가 비어 있다. 현재 상태로는 *하네스*라기보다 **"안전장치 없이 Claude Code를 bypass로 돌리는 자기개선 스크립트"**에 가깝다 — 정확히 보고서가 경고한 두 안티패턴(자기평가·격리 없는 bypass)을 포함한 채로. 다음 작업은 P0(강제·환경 기초 + 검증 자기평가 수정)가 되어야 한다.
